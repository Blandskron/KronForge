# Roadmap del Framework

- **Fuente canónica:** este documento.
- **Última revisión:** 2026-07-28.
- **Principio:** profundidad, calidad y evidencia antes que volumen.

Los roadmaps incluidos en documentos estratégicos anteriores describen su momento de diseño. Cuando exista una diferencia, prevalece este archivo.

## Orden de evolución

1. arquitectura;
2. gobernanza;
3. calidad automatizada;
4. experiencia web;
5. expansión de biblioteca y comunidad.

## Entregas completadas

### v1 — Prompt y estándar agents-first

Prompt maestro, documentación operativa y primera experiencia web.

### v2.0 — Biblioteca por dominios

Catálogo, contratos, migración de prompts y activos reutilizables.

### v2.1 — Portal y pilares AI Engineering

Context Engineering, Repository Engineering, MCP, hooks, subagentes, schema v2 y exploración por catálogo.

### v2.2 — Lectura y portabilidad

Render Markdown editorial, copia del contenido canónico, descarga de archivos y correcciones de publicación en GitHub Pages.

Las iniciativas de aprendizaje y casos reales antes asociadas a v2.2 se reprograman para v3.5 para no declararlas completadas sin evidencia.

## v3.0 — Framework gobernado y verificable

**Estado:** implementado y validado; publicación de la release pendiente.

### Objetivos

- arquitectura escalable para nuevos tipos de conocimiento;
- catálogo enriquecido y validable;
- gobernanza open source, ownership y políticas públicas;
- quality gates y validaciones automáticas;
- compatibilidad agents-first documentada sin duplicación;
- portal alineado con fuentes canónicas;
- ADR para decisiones arquitectónicas;
- roadmap y release lifecycle coherentes.

### Criterios de salida

- documentación comunitaria y GitHub templates operativos;
- catálogo, índices, rutas, IDs y versiones validados automáticamente;
- navegación y contenido público verificados en GitHub Pages;
- ninguna capacidad o compatibilidad declarada sin evidencia;
- release v3 reproducible según la política de lifecycle.

## v3.5 — Aprendizaje y casos reales

**Estado:** planificado.

### Objetivos

- enriquecer las rutas iniciales con objetivos, prerrequisitos y progresión;
- tutoriales progresivos para prompts, agentes, MCP, arquitectura, testing, seguridad y GitHub;
- casos completos de modernización, documentación y preparación agents-first;
- ejemplos con antes, después, archivos, decisiones y resultado esperado;
- relaciones y prerrequisitos navegables.

### Criterios de salida

- cada recorrido tiene objetivo, nivel, prerrequisitos y resultado;
- cada enlace resuelve a contenido canónico vigente;
- los casos pueden reproducirse sin secretos ni infraestructura ficticia.

## v4.0 — Interoperabilidad

**Estado:** planificado.

### Objetivos

- perfiles de consumo portables para agentes y equipos;
- paquetes documentales sin runtime obligatorio;
- integraciones opcionales con contratos de permisos y compatibilidad;
- exportación del catálogo y relaciones mediante formatos estables;
- soporte de versiones del portal sin duplicar activos.

### Criterios de salida

- integraciones desacopladas del núcleo;
- formatos versionados con migración;
- compatibilidad verificada por herramienta y versión cuando se declare.

## v4.5 — Evaluación y escala comunitaria

**Estado:** visión.

### Objetivos

- AI Repository Score objetivo y repetible;
- benchmarks versionados con datasets y límites documentados;
- métricas de frescura, cobertura, reutilización y descubribilidad;
- ownership por dominio cuando exista comunidad real;
- traducciones gobernadas desde contenido canónico.

### Criterios de salida

- resultados reproducibles y comparables;
- métricas resistentes a optimización superficial;
- mantenedores y revisores explícitos para cada superficie publicada.

## v5.0 — Ecosistema sostenible

**Estado:** visión.

### Objetivos

- framework estable para adopción organizacional y comunitaria;
- lifecycle de largo plazo y ventanas de soporte declaradas;
- interoperabilidad madura entre personas, agentes y herramientas;
- catálogo escalable sin perder trazabilidad ni calidad;
- comunidad capaz de mantener dominios y releases con continuidad.

### Criterios de salida

- contratos estables con migraciones probadas;
- releases, seguridad y gobernanza operables por más de una persona;
- documentación, portal y catálogo continúan siendo una sola plataforma coherente.

## Cambios al roadmap

Una modificación de objetivos o criterios requiere issue o RFC. Si cambia arquitectura, compatibilidad o secuencia de releases, también requiere ADR y aprobación según [GOVERNANCE.md](../GOVERNANCE.md).

El roadmap no es una promesa de fecha. Una entrega se declara completada solo con evidencia registrada en changelog y quality gates.
