# Roadmap propuesto de KronForge

**Estado** Propuesta para revisión del owner. Detalla entregas candidatas bajo el [roadmap vigente](ROADMAP.md) y la [gobernanza](../GOVERNANCE.md). La numeración de ciclos indica dependencias. Las versiones se deciden cuando se conozca el cambio real de compatibilidad.

## BLK-ENG-001 como primer Reference Pack

La [ficha operativa de C0](KRONFORGE_C0_BLK_ENG_001.md) reúne la revisión de ADR, el alcance del piloto, sus pruebas de aceptación y los insumos para verificar procedencia antes de C1.

El candidato **Git Flow & Agent Skills** permite probar un ciclo de ingeniería con una tarea de release que deja rastros inspeccionables. La ficha registra la revisión identificada y el cierre del piloto interno C1 para A + R, con el ensayo del autor y la excepción a la revisión independiente autorizada por el titular. El inventario de abajo describe el alcance candidato para una evolución posterior. Cualquier redistribución de derivados requiere un permiso específico.

| Componente candidato | Reuso y diseño mínimo |
|---|---|
| Guía, perfiles y política Git | Un perfil de releases versionadas con mantenimiento paralelo y un perfil de rama principal con ramas cortas como prueba de portabilidad. Compartir invariantes de autorización, revisión, evidencia y recuperación. Descubrir ramas, reglas y comandos del proyecto sin imponer nombres por defecto. |
| Prompt de diagnóstico y skill de operación | Reusar [preparación agents-first](../library/domains/ai-agent-engineering/playbooks/prepare-agents-first.playbook.md), [estado del repositorio](../library/domains/engineering-protocols/protocols/repository-state.protocol.md) y [revisión de release](../library/domains/delivery-platform/prompts/release-readiness-review.prompt.md). Una skill nueva se justifica si hay una tarea recurrente que esos activos no cubren, como preparar un plan de promoción según el perfil. Recursos indispensables viajan con la skill. |
| Workflow, plantillas y revisión | Auditar árbol y rama base → proponer cambio → preparar rama local con autorización → ejecutar gates → revisar → preparar release → decidir publicación. Reusar el [checklist pre-merge](../library/domains/quality-engineering/checklists/pre-merge.checklist.md), [plantilla de evidencia](../library/domains/engineering-protocols/templates/evidence-record.template.md), [revisión independiente](../library/domains/engineering-protocols/protocols/independent-review.protocol.md) y [preparación de publicación](../library/domains/engineering-protocols/protocols/release-readiness.protocol.md). El escenario de hotfix incluye reconciliar las líneas afectadas. |
| Script, hook y CI | Un validador comprueba contexto Git, alcance y evidencia de los gates. Un hook optativo reusa el [patrón de validación explícita](../library/domains/hooks-workflows/patterns/explicit-validation-hook.pattern.md). La misma regla se verifica en ejecución manual y CI. La instalación deja hooks y CI pendientes de activación. Incorporar un adaptador de CI solo si el escenario externo lo necesita. |
| Artefacto y recuperación | Entregar snapshot con guía, licencia, manifiesto y archivos seleccionados. Validar instalación, repetición, cambios locales, actualización y retiro. Agregar una proyección Agent Plugins de la skill cuando se pueda comparar con la vía manual. El pack piloto funciona con Git local y archivos. Las credenciales y servicios quedan fuera de los escenarios obligatorios. |

## Escenarios y evaluación

| Escenario de aceptación | Resultado exigido |
|---|---|
| Alta en repo limpio y repetición | El árbol y lock coinciden con el plan. Segunda aplicación produce diff vacío y mismos bytes, sin activar hooks ni servicios. |
| Repo con reglas propias y trabajo local | Se detecta colisión de instrucciones, archivos gestionados modificados o políticas incompatibles. El plan muestra el punto de decisión y no cambia el árbol antes de aprobación. |
| Release y hotfix | La skill y la guía producen un plan trazable, se ejecutan los gates reales del consumidor y se identifica cada línea de mantenimiento afectada. Escrituras remotas, tags y publicación requieren aprobación explícita. |
| Controles negativos | Artefacto alterado, digest ausente, destino fuera del proyecto, política más restrictiva y ampliación de permisos detienen la operación antes de activar contenido. Una compuerta sin evidencia permanece `NOT_RUN`. |
| Actualización, fallo y retiro | Un cambio de perfil o permiso invalida la aprobación previa. Un fallo intermedio permite recuperar árbol y lock. Se protege cualquier archivo ajeno o modificado y se conservan propietarios compartidos. |
| Uso externo y paridad | Revisor ajeno al autor repite desde un artefacto exacto, sin acceso al checkout del productor. Captura versión de cliente, OS, escenario, instrucciones usadas, entradas y resultados. La matriz distingue instalar, descubrir, activar y completar el resultado esperado. |

El benchmark compara una guía documental equivalente con el pack gestionado sobre tareas versionadas y variantes de repositorios. Congelar instrucciones, entradas y rúbrica, separar datos de calibración y evaluación, variar el orden entre participantes y registrar modelo, versión, permisos y presupuesto cuando intervenga un agente. Medir éxito, minutos hasta el primer resultado correcto, intervenciones humanas, pasos manuales, defectos y recuperación. Reportar tamaño de muestra, dispersión y fallos. La aceptación técnica exige que todos los escenarios obligatorios pasen y que ocurran cero efectos no autorizados en las ejecuciones observadas. Los umbrales de mejora se acuerdan antes de medir en función de una línea base. Una muestra pequeña permite detectar fricción, con alcance limitado para generalizar efectos.

El gate de cada ciclo combina la [puerta vigente](QUALITY_GATES.md), resultados del candidato y aprobación correspondiente. Los resultados con excepción registran condición, autoridad, vigencia y planes de revisión. Los cambios a los bytes entregados, a la guía o al mecanismo de instalación exigen repetir la validación externa relevante. El informe público usa artefactos y evidencias saneados.
