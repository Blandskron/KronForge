# Auditoría de evolución de KronForge

**Fecha de corte** 2026-11-27 · **Base local** `664c3edb418a20aff24738ab70851044d1431c3e` / `v3.4.0`.

**Seguimiento al integrar en main.** En `c354eb6` ya están completos los contratos estructurados de los 65 activos y los tres dominios antes vacíos cuentan con activos. El README, la identidad del portal, los casos y el CI de navegador también evolucionaron desde el corte. Los conteos de esta auditoría describen su línea base y la [ficha de C0](../KRONFORGE_C0_BLK_ENG_001.md) registra la verificación posterior de BLK-ENG-001 y el estado de C1.

KronForge se usa aquí como nombre de trabajo para la evolución del Agents First Framework. La unidad de adopción propuesta es un pack pequeño y versionado que combina activos existentes y se puede probar en un repositorio consumidor. El núcleo conserva el flujo **Copiar → Pegar → Auditar → Aprobar → Aplicar**.

## Alcance y método

Se contrastaron el árbol y el historial local, el prompt maestro, la arquitectura, los siete ADR vigentes, el catálogo y su schema, los protocolos AFP, las proyecciones, el portal, los validadores, CI y la gobernanza. Los conteos debajo corresponden a esa revisión. La investigación consultó especificaciones, documentación de implementadores y un estudio empírico primario. La compatibilidad documentada por un proveedor queda pendiente de verificación en una instalación real. Se buscó BLK-ENG-001 por ID y título en el árbol y en fuentes públicas, incluida la lista de repositorios públicos de Blandskron. Quedaron sin verificar su fuente canónica, versión, licencia, contenido y resultados.

La línea base pasó `npm run quality` en Windows con Node.js 24.15.0. El resultado fue 12 grupos de validación sin errores, 34 pruebas unitarias aprobadas, 134 rutas del portal verificadas en el servidor local y AI Repository Score de 98/100. Quedaron dos advertencias por los tres dominios vacíos y los 62 contratos parciales.

## Estándares y distribución

Fuentes consultadas el 2026-11-27. Las revisiones sin versión publicada se identifican por URL y fecha de consulta. Esta matriz registra la investigación de diseño. Los futuros activos canónicos trasladarán solo las afirmaciones que usen a sus `specRefs` y seguirán la [política de frescura](../SPEC_FRESHNESS.md).

| Fuente y versión observada | Qué resuelve y decisión |
|---|---|
| [Agent Skills](https://agentskills.io/specification) | Adoptar la carpeta con `SKILL.md`, nombre y descripción, más recursos y scripts locales cuando hagan falta. La publicación recomienda mantener el cuerpo por debajo de 500 líneas, límite que el repo aplica como política. `allowed-tools` es experimental y representa una declaración que requiere enforcement del host. El formato deja al cliente descubrimiento, instalación y permisos. |
| [AGENTS.md](https://agents.md/) | Usar Markdown para reglas persistentes del repositorio y contexto de trabajo. La precedencia de archivos anidados debe comprobarse en cada cliente probado. Ofrecer un fragmento revisable y conservar la autoridad del proyecto consumidor. |
| [Agent Plugins 1.0.0](https://agent-plugins.org/specification) y su [schema](https://agent-plugins.org/schemas/1.0.0/plugin.schema.json) | Reutilizar el `plugin.json` raíz para cargar skills y, cuando proceda, configuraciones MCP. Preservar rutas confinadas al plugin. El formato deja fuera el contrato de adopción de documentación, gates, permisos y actualizaciones del proyecto. Extensiones por cliente se proyectan desde adaptadores. |
| [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28) y [MCP Registry](https://modelcontextprotocol.io/registry/about) | MCP sirve para conectar herramientas, recursos y prompts durante la ejecución. El Registry, documentado en preview, indexa metadata `server.json` y apunta a paquetes o endpoints. Usarlos solo para integraciones MCP optativas que los necesiten. Evaluar revisión, capacidades, transporte, autenticación, origen y permisos efectivos. |
| [A2A v1](https://a2a-protocol.org/latest/) | Mantenerlo como interfaz optativa de interoperabilidad entre agentes con una necesidad de comunicación remota demostrada. La delegación local sigue el protocolo AFP aplicable. |
| [Vercel skills](https://github.com/vercel-labs/skills) | Descubrimiento e instalación por cliente, control de actualizaciones y lock de proyecto documentado con commit y hash. Reutilizable para skills independientes. Registrar versión y modo probado, ya que algunos flujos se publican como experimentales. |
| [GitHub CLI `gh skill`](https://cli.github.com/manual/gh_skill), [install](https://cli.github.com/manual/gh_skill_install) y [update](https://cli.github.com/manual/gh_skill_update) | Flujo en preview con pinning por tag o commit, scopes y metadatos de procedencia inyectados. Probar como adaptador para skills. Las transformaciones del instalador cambian los bytes y deben quedar fuera de la ruta gestionada, o registrarse como proyección específica. |
| [OpenAI Plugins](https://developers.openai.com/plugins/build/plugins), [VS Code](https://code.visualstudio.com/docs/agents/reference/agent-plugin-reference) y [Copilot](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/) | Documentan soporte de Agent Plugins y canales de distribución propios. Priorizar dos clientes con familias distintas cuando haya un artefacto. La declaración de un canal o cliente sirve para seleccionar pilotos. |
| [Marketplace de Claude Code](https://code.claude.com/docs/en/plugins/create-marketplace) y [dependencias](https://code.claude.com/docs/en/plugins/dependencies) | Canal propio con resolución de dependencias por rangos. Usar únicamente mediante adaptador y validar su semántica y alcance. Comparar el mantenimiento con la exportación estándar antes de añadirlo. |
| [Git hooks](https://git-scm.com/docs/githooks) y [modelo Git Flow original](https://nvie.com/posts/a-successful-git-branching-model/) | Git aporta eventos locales útiles para feedback. La autoridad del gate debe residir en la política del proyecto y su validación explícita. El autor de Git Flow lo sitúa en software con releases versionadas o líneas soportadas y sugiere flujos más simples para entrega continua. |
| [JSON Schema 2020-12](https://json-schema.org/draft/2020-12), [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html) y [SPDX](https://spdx.org/licenses/) | Reutilizar contratos de forma, versionado de interfaces y licencia. Las invariantes entre archivos, las autorizaciones y la compatibilidad de comportamiento requieren validación adicional. |
| [in-toto Attestation](https://github.com/in-toto/attestation), [SLSA Provenance v1.2](https://slsa.dev/spec/v1.2/provenance), [Sigstore](https://github.com/sigstore/cosign) y [TUF](https://theupdateframework.github.io/specification/latest/) | Reusar declaraciones por digest, procedencia de build y verificación de identidad cuando se distribuyan artefactos publicados. Considerar TUF si la actualización automática justifica proteger contra metadatos obsoletos o rollback hostil. La implementación depende de la política de confianza aprobada. |

Un estudio empírico preliminar sobre Agent Plugins reporta pérdida de componentes específicos de clientes y colisiones de nombres en el corpus analizado. Sugiere probar el comportamiento tras cargar una capacidad y prevalidar destinos al componer un pack. El corpus mide plugins públicos de terceros y aporta una hipótesis para nuestras pruebas de interoperabilidad. [Estudio y metodología](https://arxiv.org/abs/2609.23809).
